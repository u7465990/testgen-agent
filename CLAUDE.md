# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

TestGen Agent is a standalone Python tool that automatically generates **JUnit unit tests (4 or 5)** for Java projects using an LLM (OpenAI, Anthropic, or any Anthropic-compatible endpoint such as DeepSeek). It parses a Java project, extracts methods and branch conditions, generates rule-based test targets, asks an LLM to write a test for each target, compiles the results with `javac`, repairs compilation failures by feeding errors back to the LLM, measures how good the result actually is, and writes a Markdown/JSON/CSV/console report. The only runtime the Python code itself exercises is the LLM and `javac`/`mvn` — the "tests" are generated JUnit files, verified by running `mvn test` against a real Java project (see `examples/demo-project`). There is no Python test suite.

**The framework is detected, not assumed.** `target_profile.py` reads the JUnit version off the project's resolved test classpath and the Java level off its build file (falling back to the compiled `.class` major version, then the running JDK). This mirrors what Surefire itself does, and it is why the same agent emits `org.junit.Assert` for `examples/demo-project` and `org.junit.jupiter.api.Assertions` for `examples/demo-project-junit5`. `--junit {auto,4,5}` and `--java {auto,8,11,17,21}` override it. Do not introduce a global JUnit default — `auto` is the design.

**Quality is measured, not assumed.** Compilation success only proves a file parses — an empty test class compiles fine. Phase 8 therefore reports mutation score (PiTest) as the headline metric, plus assertion density and empty-test-class detection.

The verified demo run (`examples/demo-project`, Maven, Java 8, 4 classes) produced 40 tests with 100% compile rate, 36/38 runtime pass rate, and a **75–84% mutation score (60–67 of 80)** — on par with the human-written baseline (83.98%) in the ICST 2026 replication study. The second demo, `examples/demo-project-junit5` (same 4 classes, Maven, **Java 17, JUnit 5**), produced 40 tests, 40 executed, 100% compile, and **76–86% mutation score (61–69 of 80)** across two runs. Full details are in `README.md`.

**Quote the range, not a single number.** Every run regenerates the tests and the LLM does not repeat itself; two measured runs scored 83.8% and 75.0%. Pinning one figure as *the* result is the overclaiming this project exists to avoid.

## Commands

Requires Python 3.10+, `javac` (JDK on `JAVA_HOME`, not a JRE), and an LLM API key. Maven is optional but required for classpath resolution, Phase B, and Phase 8 — and PiTest itself needs a **JDK 11+**, even when the generated tests target Java 8. On Windows `mvn.cmd` is invoked through `cmd /c` automatically.

```bash
# Discover methods a project would target (no LLM calls, fast)
python main.py analyze <project-path>

# Full pipeline: discover → extract → generate → repair → report
python main.py generate <project-path>

# Re-compile already-generated _Test_*.java files and report status
python main.py repair <project-path>
```

API keys: `OPENAI_API_KEY` (default provider `openai`, model `gpt-4o-mini`), or for Anthropic/DeepSeek use `--provider anthropic` plus `ANTHROPIC_API_KEY` (falls back to `ANTHROPIC_AUTH_TOKEN`) and `ANTHROPIC_BASE_URL` (e.g. `https://api.deepseek.com/anthropic`).

Install as a package (`pip install -e .`) to get a `testgen-agent` console script; otherwise run `python main.py` from the repo root. `requirements.txt` pins the four runtime deps (javalang, openai, anthropic, pyyaml) — there is no dev/test dependency set.

Useful flags: `--package <pkg>` (takes a **package name** like `com.demo`, repeatable, not a class name), `--exclude <method>`, `--skip-private`, `--include-constructors` (off by default — constructors are not targeted otherwise), `--target-types normal boundary` (also accepts `exception path reflection`), `--max-per-method N` (default 10), `--max-repair N` (default 3), `--extraction-mode {python,sootup}`, `--junit {auto,4,5}` and `--java {auto,8,11,17,21}` (both default `auto` = follow the project), `--temperature F` (default 0.2), `--api-key K` (overrides the env var), `--output-dir D` (default: the project's `src/test/java`), `--no-coverage` (skips the JaCoCo phase B), `--no-mutation` (skips the PiTest phase 8), `--pitest-version V` (default 1.15.0), `--no-resume` (ignore the JSONL checkpoint and regenerate from scratch), `--report-format {json,csv,both,md,all}` (default `all`), `-v/--verbose`, `--provider anthropic --model <model>`.

Reproducing the verified demo run:

```bash
python main.py generate examples/demo-project \
  --provider anthropic --model deepseek-v4-flash --max-per-method 2 --no-coverage
cd examples/demo-project && mvn test   # must use `clean` if re-running: mvn clean test
```

Do **not** add a `mvn compile` step first. `JavaCompiler.ensure_project_built()` builds the project before generating, because `javac` cannot resolve the project's own types otherwise — and an earlier "compile first" instruction hid exactly that bug (a clean checkout scored 18/40 compile rate; see README fix 9).

Note: generated test files use the naming convention `ClassName_method_ParamType_Test_Type_N`; Maven projects must configure surefire `<includes>**/*_Test_*.java</includes>` for them to be executed (see `examples/demo-project/pom.xml`).

## Architecture

The pipeline is orchestrated by `TestGeneratorAgent.run()` in `agent.py`, which drives 8 phases. `AgentConfig` (`config.py`) is the single configuration object threaded through every module.

Phases 2–4 share one console banner (`=== Phases 2-4: Filtering, Targets & Generation (streaming) ===`) because they run as a single streaming loop over source files — do not go looking for a "Phase 3" line in the log.

```
project/ → [1] java_analyzer → [2] method_extractor → [3] target_generator
        → [4] prompt_manager + llm_client + test_writer → [5] compiler + repair_loop (Phase A)
        → [6] coverage_analyzer + repair_loop (Phase B, optional)
        → [7] recompile survivors → [8] quality_analyzer → report_generator
```

- **Phase 0 — Target detection** (`target_profile.py`): runs at the top of Phase 1, right after the build. `detect_into()` fills the shared `TargetProfile` in place — Java version from `pom.xml` (`maven.compiler.release` > `source`/`target`/`java.version`, then `build.gradle`, then the compiled `.class` major version, then `javac -version`), JUnit version from the resolved classpath (`junit-jupiter`/`junit-platform` → 5, else `junit:junit` → 4; both present means a migration in progress and **5 wins**). The profile is created in `TestGeneratorAgent.__init__` and passed to the extractor, target generator, compiler and repair loop, all of which **read it at use time** rather than copying the values — so detection can happen after those objects are built. Result lands in `report.target_profile` with a `*_source` string per version so a wrong guess is traceable.
- **Phase 1 — Project analysis** (`java_analyzer.py`): `JavaProjectAnalyzer` detects the build tool (Maven/Ant/Gradle/manual via `pom.xml`/`build.gradle`/`build.xml`), walks `src/main/java` for `.java` files, and resolves the classpath. `resolve_classpath()` runs `mvn dependency:build-classpath -Dmdep.includeScope=test` (test scope is required so JUnit is on the compile classpath) and caches to `target/classpath.txt`. The classpath separator is `;` on Windows, `:` elsewhere. The phase then calls `JavaCompiler.ensure_project_built()` (`compiler.py`) — if no `target/classes`/`build/classes`/`bin` exists it runs `mvn -q compile -B` (or the Gradle/Ant equivalent) and **invalidates the cached classpath**, because it was resolved before the classes directory existed.
- **Phase 2 — Method extraction** (`method_extractor.py` + `extractor/`): `MethodExtractor` is a facade over a backend. The default `JavalangBackend` (`extractor/javalang_backend.py`) parses source with `javalang`, producing a `MethodInfo` per method. `SootUpBackend` (`extractor/sootup_backend.py`) is an opt-in (`--extraction-mode sootup`) that additionally compiles `extractor/SootUpExtractor.java` and runs it as a subprocess to attach Jimple IR — it requires a compiled `target/classes` and SootUp JARs, and silently falls back to javalang-only on any failure.
- **Phase 3 — Target generation** (`target_generator.py`): `TargetGenerator` turns each `MethodInfo` into descriptive target strings the LLM must satisfy: `[Normal]`, `[Boundary]` (one per parameter, from a type→edge-value table), `[Exception]` (one per declared checked exception), `[Path]` (two per extracted branch condition, true/false), `[Reflection]` (for private methods). Results are capped at `max_tests_per_method`.
- **Phase 4 — LLM generation** (`prompt_manager.py`, `llm_client.py`, `test_writer.py`): `PromptManager` loads the four `.txt` templates from `prompts/` and substitutes `#{FQN}#`, `#{Signature}#`, `#{SourceCode}#`, `#{BranchConditions}#`, `#{ClassContext}#`, `#{AllowedImports}#`, `#{ThrowsExceptions}#`, `#{Modifiers}#`, `#{GenerationTarget}#` (`#{JimpleCode}#` is empty unless the sootup backend ran). `LLMClient` wraps OpenAI and Anthropic chat APIs with exponential-backoff retries. `TestWriter` extracts the Java block from the response, dedupes imports, renames the class to the deterministic `ClassName_method_ParamType_Test_Type_N` form, writes the file to `src/test/java/<package>/`, and also derives the package from the FQN.
- **Phase 5 — Compilation repair (Phase A)** (`compiler.py`, `repair_loop.py`): `JavaCompiler` invokes `javac` with `-source 8 -target 8` against the resolved classpath. `RepairLoop.repair_compilation()` runs up to `max_compile_attempts` rounds: compile → on failure, send the javac error + code back to the LLM via `render_repair_prompt()` → write the fix → recompile. It force-fixes the `package` declaration before each compile and injects a reflection hint when the error mentions `private`.
- **Phase 6 — Coverage improvement (Phase B, optional)** (`coverage_analyzer.py`, `repair_loop.improve_coverage()`): only when `--no-coverage` is absent. Runs `mvn clean test jacoco:report`, parses `target/site/jacoco/jacoco.xml`, finds methods below `branch_coverage_target` (0.98), and generates `[MissingBranch]` tests, up to `max_runtime_rounds` (3). Requires Maven + JaCoCo configured in the target project; on any failure it prints a warning and returns no new tests.
- **Phase 7 — Final verification** (`agent.py`): recompiles every surviving test file against the classpath (this is where `compilation_rate` comes from) and builds the per-method `MethodReport` list.
- **Phase 8 — Test quality** (`quality_analyzer.py`): `TestQualityAnalyzer` computes metrics from the generated sources — `empty_test_classes` (parses `@Test`, comments stripped first; the regex also lists `@ParameterizedTest`/`@RepeatedTest`/`@TestFactory`/`@TestTemplate`, because `@Test\b` alone does not match any of them and a JUnit 5 class using only those would be misreported as empty) and `assertion_density` (`assert*`/`fail(` per `@Test` method). `MutationAnalyzer` then runs PiTest via Maven and parses `target/pit-reports/mutations.xml` into a `MutationResult`. Skipped with `--no-mutation`; degrades gracefully if Maven or the plugin is unavailable.
- **Reporting** (`report_generator.py`): `AgentReport` is printed to console and written to `.testgen-agent/report.md` (human-facing, mutation score first), `report.json`, and `report.csv`.
- **Logging** (`runlog.py`): `setup_logging()` attaches the `testgen` logger to `.testgen-agent/run.log` (mode `w`, one log per run). The file handler is always on and at DEBUG; `--verbose` only adds a stderr handler. Called from `main.main()` (covers `analyze`/`repair`) and `TestGeneratorAgent.run()`; it is idempotent and never raises. Instrumentation lives where diagnostics would otherwise be swallowed: `compiler.compile()` records the javac error, `llm_client` records request/response sizes and retries, `java_analyzer.resolve_classpath()` records the resolved entries, and `agent._phase()` records per-phase elapsed time.

## Key data model and conventions

- **`MethodInfo`** (`method_extractor.py`) is the central data structure flowing through the whole pipeline: FQN, signature, source code, `branch_conditions` (extracted via regex over the body for `if`/`while`/`for`/`catch` predicates), `class_context` (fields + constructors), `allowed_imports` (the version-appropriate JUnit set + reflection + `java.lang.reflect` always allowed, plus project imports), `throws_exceptions`, and flags (`is_private`, `is_static`, `is_abstract`, `is_constructor`).
- **`TestFile`** (`repair_loop.py`) wraps a generated test file with its `compiles` / `runnable` / `compile_attempts` status.
- **Prompt templates** live in `prompts/`: `generate_system.txt`/`generate_user.txt` define the persona, strict import restriction, the framework-specific syntax/exception rules, and reflection requirement for private methods; `repair_system.txt`/`repair_user.txt` are for the compile-fix loop.
- **Prompt versioning** (`prompt_manager.py`): the version-dependent rule text is **not** duplicated into a second template set. The templates carry `#{JUnitVersionLabel}#`, `#{JUnitExceptionRule}#`, `#{JUnitSyntaxRule}#` and `#{JUnitSyntaxRuleRepair}#`; `PromptManager._framework_replacements()` supplies the JUnit 4 or 5 wording. Substitution is plain `str.replace` — the mechanism the templates already used — and it now runs on the **system** prompt too (which previously came back verbatim). For JUnit 5 the exception rule *requires* a lambda (`assertThrows` takes an `Executable`) and explicitly bans the anonymous-inner-class form. For JUnit 4 the exception rule is the original wording **verbatim**; the syntax rule is reworded only to make the Java level dynamic instead of hard-coding "JDK 8" (the prohibitions are the same set, spelled out: no lambdas, no method references, no Streams, no `var`). Target-description text in `target_generator.py`/`repair_loop.py` is likewise unchanged for JUnit 4 — verified by diffing generated target strings. `allowed_imports` is versioned the same way (`always_allowed(junit_version)` in `method_extractor.py`), and project imports of the *other* JUnit are filtered out so a mid-migration project cannot smuggle `org.junit.Assert` into a JUnit 5 test.
- **The templates forbid mocking** (no Mockito, no test doubles). This is a hard product boundary, not an oversight: any class whose behaviour depends on an injected dependency (service, repository, client) generally cannot get a runnable generated test. It is the single biggest gap for real-world projects, so treat "add mocking support" as a feature request that changes the prompt contract — not a bug.
- **Claude Code skill**: the real skill definition is `references/skill-draft-SKILL.md` — a `SKILL.md` with `name`/`description` frontmatter that must be copied to `.claude/skills/generate-tests/SKILL.md` with `<REPO>` replaced by this repo's absolute path. `skill.yaml` + `skill_entry.py` are a **legacy CLI wrapper that never worked** (they assume a `command:`/`arguments:` templating engine that Claude Code does not have; `skill_entry()` builds an `AgentConfig` and returns a summary dict, but no invocation path reaches it). Kept only for history — do not document them as the way to run the skill.

## Repo layout

The ~19 Python modules sit flat at the repo root (not in a package directory) and use **absolute flat imports** — `from config import AgentConfig`, `from java_analyzer import JavaProjectAnalyzer`. There is no relative-import layer to lean on, so a new module is imported the same way and `python main.py` must be run from the repo root.

- `examples/demo-project/` — the verified Maven/Java 8/**JUnit 4** demo (4 classes). `verified-results/` holds archived `report.json`, `report.csv`, and surefire output from a past run; the generated tests are checked in under `src/test/java/com/demo/`.
- `examples/demo-project-junit5/` — the **same 4 classes** with a JUnit 5 / Java 17 pom (`junit-jupiter`, surefire 3.x, and `pitest-maven` declaring `pitest-junit5-plugin`). Its whole purpose is to prove framework detection works end to end. Commit-free: its generated tests are reproducible with `python main.py generate examples/demo-project-junit5 --max-per-method 2 --no-coverage`.
- `target_profile.py` sits at the repo root like the other modules and must stay dependency-free (stdlib only) — the extractor and compiler both import it, and it is imported before much else is wired up.
- `references/` — contains only the skill draft (see the skill bullet above).
- `extractor/` — the pluggable backend package; `prompts/` — the four prompt templates.

**Untracked scratch files at the root are not part of the tool**: `测试Agent-讨论纪要.md` (a long Chinese design discussion), `TestGen演示步骤详解.md` (a demo walkthrough), `ideas.md` (line-by-line reading notes on `main.py`/`config.py`), and `fasd` (a stray algorithm exercise with no connection to this project). Nothing in the code references them. Don't treat them as documentation to keep in sync, and don't let their Chinese naming convention leak into source — the Python is English-only.

## Gotchas

- **Windows**: `javac` resolution requires `JAVA_HOME` to point at a JDK; `mvn` on Windows is `mvn.cmd` and must be run through `cmd /c` (handled in `java_analyzer._resolve_maven_classpath`). Do not hard-code Unix paths/separators.
- **Console encoding — keep output ASCII.** The Windows console codepage here is GBK, which covers box-drawing characters (`─`) but *not* `✓`/`✗`/emoji. `print("  ✓ ...")` raises `UnicodeEncodeError` and kills the command. Use `[OK]`/`[FAIL]`. The Chinese text in `report.md` is fine — that is a file, written as UTF-8.
- **`--verbose` used to be dead code** — set in `AgentConfig` and never read. It now controls whether debug logging is echoed to the console; the log file is written regardless.
- **Anthropic-compatible models (e.g. DeepSeek) return a `ThinkingBlock` before the text block** — `LLMClient` concatenates only `type == "text"` blocks; keep this when changing the client.
- **The classpath must include test-scope dependencies** (`-Dmdep.includeScope=test`); without it JUnit is missing and every generated test fails to compile.
- **Compilation success ≠ a useful test** — a file can compile and contain no `@Test` method at all. Never treat `compilation_rate` as evidence of quality; use `mutation_score`. Phase 8 reports empty test classes explicitly, which is why the demo shows 40 compiled but only 38 executed.
- **PiTest on a JUnit 5 project needs `pitest-junit5-plugin` in the target pom, and there is no way to pass it on the command line.** The plugin is invoked as a fully-qualified GAV with bare `-D` properties, so there is no channel for a plugin dependency — it only merges when the pom declares `pitest-maven` with that `<dependencies>` entry. `_run_mutation_analysis()` detects the combination (JUnit 5 + `pom_declares(..., "pitest-junit5-plugin")` is False) and skips with an explicit message. Verified working: with the declaration present, the fully-qualified-GAV invocation **does** pick the dependency up (see `examples/demo-project-junit5/pom.xml`, which declares it deliberately). Adding it to a *user's* pom is out of scope — the agent only reads poms, never writes them.
- **`[Exception]` targets only cover declared checked exceptions.** They come from `method.throws_exceptions`, i.e. the `throws` clause. A method that throws `IllegalArgumentException` from its body gets no exception target, so the LLM may assert it with `try/catch` rather than `assertThrows`. This is separate from — and was for a while confused with — the wiring bug below. Generating targets from `throw new X(...)` in `method_body` is the follow-up.
- **Every call site of a prompt renderer must be updated when its signature grows.** `render_generate_prompt` gained a `profile` parameter so the system prompt could carry version-specific rules (`#{JUnitExceptionRule}#`, `#{JUnitSyntaxRule}#`). Two call sites were updated; `agent.py`'s main generate path was not, so `_fill_framework` silently fell back to `TargetProfile()` = **JUnit 4 / Java 8** and the generate prompt told every project "Do NOT use assertThrows() (not available in JUnit 4)" — while the target text, built from the correctly-shared profile, asked for JUnit 5. The result was zero `assertThrows` and an anonymous `new Executable() { ... }` that satisfied both readings. It hid well because the **repair** prompt *did* receive the profile, so only first-pass generation was wrong, and because the generated files were still valid JUnit 5. A silent default (rather than a required argument) is what let it pass unnoticed — prefer making such parameters required, or assert on them.
- **`max_tokens` truncation presents as a javac syntax error.** `llm_client` sends `max_tokens` for the Anthropic-family path (the API requires it). At 4096 a longer JUnit 5 test came back cut mid-string, which surfaced as `unterminated string literal` at EOF — and because the file could not compile, `mvn test-compile` failed, PiTest never ran, and the whole Phase 8 was skipped. Default is now 8192 and `--max-tokens` overrides it; `LLMClient._warn_if_truncated()` reads `response.stop_reason == "max_tokens"` and warns explicitly, which is the only reliable signal. If mutation analysis reports "did not run", check for an uncompilable generated file first — `MutationAnalyzer.describe_failure()` now distinguishes that case from a genuinely missing Maven.
- **PiTest requires a green suite** — it aborts with "did not pass without mutation" if *any* test fails. `_run_mutation_analysis()` handles this: it parses the offending test classes out of PiTest's output, retries with `-DexcludedTestClasses`, and records them in `report.mutations_excluded_tests`. Keep that retry — a single failing generated test would otherwise kill the whole phase.
- **Agent output lives in `.testgen-agent/` at the project root, NOT in `target/`** — the coverage phase runs `mvn clean`, which deletes `target/` and would take the resume checkpoint and all reports with it. `_migrate_legacy_checkpoint()` copies forward a checkpoint left by an older version at the old `target/testgen-agent/` path.
- **Resume/checkpoint** (`agent.py` + `checkpoint.py`): `generate` processes source files in a streaming loop and records each successfully-compiled test to `.testgen-agent/checkpoint.jsonl` (JSONL; each line stores the full `MethodInfo`). A re-run skips recorded tests so an interrupted run doesn't re-call the LLM; the global target counter still advances for skipped items so class names match a full run. Phase B (coverage) and Phase 8 tests are not checkpointed.
- **`main.py repair` was broken until recently** — it used `JavaProjectAnalyzer` without importing it, and printed `✓`/`✗` (which crash on GBK). Both fixed; note it only *reports* compile status, it does not drive the LLM repair loop despite the name.
- **`resolve_classpath()` dedupes** — the Maven resolver both returns its entries and caches them to `target/classpath.txt`, which the pre-cached block then re-reads. Without the dedupe every dependency appears twice (and again when passed through `compile(extra_classpath=...)`).
- `--package` filters on the package name only, not the class name; the demo classes all live in `com.demo`.
- **CLI defaults and `AgentConfig` defaults differ.** `main.build_config()` sets `report_format="all"` and `target_types` including `reflection`; the dataclass defaults are `report_format="json"` and a `target_types` list *without* `reflection`. A programmatic caller that constructs `AgentConfig` itself (as `skill_entry.py` does, pass `report_format="json"`) silently gets no `report.md` and no reflection targets for private methods. Set these explicitly when building a config in code.
- The `sootup` extraction backend (`extractor/`) is legacy/opt-in and degrades gracefully; the default `python` mode (javalang, no Jimple) is what the verified run used.
